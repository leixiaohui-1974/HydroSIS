# 第七章 二次开发与扩展指南

本章聚焦 HydroSIS 框架在二次开发与生态扩展方面的设计理念、代码接口与实战流程。内容涵盖插件式模型注册、配置增量维护、工作流钩子、评估与报告自定义、测试策略，以及示例驱动的扩展样板，旨在帮助研发人员高效构建专有水文模块或行业化解决方案。

## 7.1 扩展哲学与模块分层

HydroSIS 以 Python 包形式暴露模型、配置、评估和报表等核心接口，`hydrosis.__init__` 将常用实体（模型、配置、工作流与报告工具）集中导出，方便外部项目以最少 import 即可接入。【F:hydrosis/__init__.py†L3-L32】
整体架构遵循“配置驱动 + 注册表 + 工作流编排”的思路：

- **核心模型层**：`HydroSISModel` 负责耦合子流域、参数区以及产流/汇流模型，实现局地径流计算与下泄累积，确保扩展组件只需实现标准接口即可融入整体运算。【F:hydrosis/model.py†L32-L115】
- **配置层**：`ModelConfig` 及其子配置类（如 `RunoffModelConfig`、`RoutingModelConfig`、`ParameterZoneConfig`）定义 YAML/JSON 映射规则，支持逐字段序列化与反序列化，为新增参数或场景提供统一入口。【F:hydrosis/config.py†L79-L190】
- **评估与工作流层**：`run_workflow` 将模型实例化、情景应用、结果持久化与评估报表整合为一条流水线，是扩展自定义钩子和自动化脚本的核心落点。【F:hydrosis/workflow.py†L168-L267】

理解上述分层后，开发者可按需在任一层插入新功能，而不必修改其余模块。

## 7.2 产流与汇流模型的插件式扩展

### 7.2.1 注册表机制

HydroSIS 为产流与汇流模型分别定义抽象基类与注册表：

- `RunoffModel`/`RunoffModelConfig` 通过 `REGISTRY` 字典维护可用模型，并在 `build()` 时按 `model_type` 查找实际实现；若未注册则抛出显式异常，防止配置引用不存在的算法。【F:hydrosis/runoff/base.py†L11-L55】
- `RoutingModel`/`RoutingModelConfig` 采用相同模式，确保流量路由算法可热插拔扩展。【F:hydrosis/routing/base.py†L11-L55】

这意味着新增模型只需继承基类、实现接口，并在模块底部调用 `RunoffModelConfig.register("key", Class)` 或 `RoutingModelConfig.register("key", Class)` 完成挂载。【F:hydrosis/runoff/scs_curve_number.py†L12-L33】【F:hydrosis/routing/lag.py†L12-L22】

### 7.2.2 新模型开发步骤

1. **创建模块**：在 `hydrosis/runoff/` 或 `hydrosis/routing/` 下新建文件，继承对应基类并实现 `simulate()` 或 `route()` 方法，充分利用传入的 `Subbasin` 参数（包含面积、下游指向与参数映射）。【F:hydrosis/model.py†L18-L90】
2. **参数约定**：构造函数会接收配置中的 `parameters` 字典，建议在 `__init__` 中完成默认值转换与单位校正，参考 SCS 曲线数法对 `curve_number` 等参数的处理方式。【F:hydrosis/runoff/scs_curve_number.py†L15-L30】
3. **注册标识**：在模块末尾调用注册函数，将新模型暴露给配置层。【F:hydrosis/runoff/scs_curve_number.py†L33-L33】
4. **配置引用**：在 YAML/JSON 的 `runoff_models` 或 `routing_models` 列表中新增条目，指定 `model_type` 为上述注册名，即可在参数区或子流域中引用。【F:config/example_model.yaml†L34-L83】

### 7.2.3 参数区与网络一致性

`ParameterZoneBuilder` 通过控制点收集上游子流域并避免重复分配，确保新增模型能按区域覆盖下游分水岭；若控制点不存在将抛出 `KeyError`，开发者在扩展配置时需同步维护子流域定义。【F:hydrosis/parameters/zone.py†L48-L97】
同时，`accumulate_subbasin_flows` 对局地径流的时间长度与网络拓扑进行严格校验，一旦缺少子流域或出现环路会即时报错，保障扩展后的网络仍满足树状结构要求。【F:hydrosis/utils/network.py†L11-L107】

## 7.3 情景、配置与 I/O 的增量维护

`ModelConfig` 支持 YAML/JSON 的双通道加载，当环境缺少 PyYAML 时，示例脚本会自动回退到 JSON 解析，方便在轻量环境或部署流水线中复用配置模板。【F:examples/run_sample_workflow.py†L35-L75】
`ScenarioConfig` 将情景修改存储为“子流域 → 参数字典”的映射，`apply_scenario` 会遍历模型中的 `Subbasin` 并执行参数更新，开发者可通过新增情景条目实现敏感性分析或调度策略评估。【F:hydrosis/config.py†L102-L193】

在 I/O 层面，`IOConfig` 允许覆盖结果、图像与报告目录；新增模块如需写入自定义产物，可在工作流执行后调用 `write_time_series` 或 `write_simulation_results` 将新序列落盘，保持目录结构统一。【F:hydrosis/config.py†L79-L109】【F:hydrosis/io/outputs.py†L10-L30】

## 7.4 工作流钩子与评估扩展

`run_workflow` 暴露多个开关参数：可选择执行哪些情景、是否持久化结果、是否生成评估报告。函数内部通过 `_instantiate_model`、`_run_model`、`_collect_candidate_simulations` 等私有助手拆解流程，便于在外部封装时复用其中任意阶段。【F:hydrosis/workflow.py†L48-L226】

评估部分基于 `SimulationEvaluator` 与 `ModelComparator`：前者维护“指标名 → 函数”映射与指标方向，后者负责计算逐子流域得分并聚合排序。新增评价指标时，可编写函数并在实例化 `SimulationEvaluator` 时传入自定义 `metrics` 与 `orientations`，或直接扩充默认字典。【F:hydrosis/evaluation/comparison.py†L23-L128】【F:hydrosis/evaluation/metrics.py†L15-L90】

若需要生成特制报告，`generate_evaluation_report` 提供挂钩：它使用 `MarkdownReportBuilder` 构建章节与表格，支持插入图像、排序列表与额外描述。开发者可先调用该函数获取基础报告，再追加自定义段落或图表路径，实现企业化输出。【F:hydrosis/reporting/markdown.py†L23-L226】

## 7.5 报告与可视化自定义

`MarkdownReportBuilder` 具备添加标题、段落、表格、列表、图片与水平线等方法，可单独用于生成项目文档或运行日志；其 `write()` 方法会自动创建目录并以 UTF-8 保存，适用于批量生成评估记录。【F:hydrosis/reporting/markdown.py†L23-L75】
在生成图表时，内部 `_generate_metric_figures` 与 `_generate_hydrograph_figures` 分别调度 `plot_metric_bars` 与 `plot_hydrograph`，并在缺少绘图库时优雅降级，提示开发者缺失依赖。扩展新图表时，可参照该模式新增辅助函数并在报告流程中插入对应调用。【F:hydrosis/reporting/markdown.py†L99-L226】

## 7.6 自动化测试与质量保障

仓库提供多组单元测试验证配置构建、工作流执行与报告生成，为二次开发提供参考：

- `tests/test_examples.py` 构建最小配置验证模型实例化、参数区分配与情景应用，适合作为新增模型的单元测试模板。【F:tests/test_examples.py†L18-L200】
- `tests/test_workflow.py` 以临时目录运行完整工作流，断言结果持久化、情景得分与报告生成，可在集成扩展后复用该脚本进行回归测试。【F:tests/test_workflow.py†L23-L169】
- `tests/test_reporting.py`（未展示）验证 Markdown 报告与图表生成功能，建议在自定义报表逻辑时参考其断言结构。

建议在新增功能后：

1. **补充单元测试**：围绕新模型、指标或报告 API 编写快速测试，确保关键逻辑被覆盖。
2. **利用临时目录**：参考工作流测试，通过 `tempfile.TemporaryDirectory()` 构建隔离环境，避免污染真实数据目录。【F:tests/test_workflow.py†L120-L169】
3. **持续集成**：在 CI 中运行 `pytest` 并校验文档生成是否成功写入预期路径。

## 7.7 自定义模块开发案例

以下示例演示如何基于现有框架扩展一个“自定义滞后-衰减混合”路由模型，并在配置与工作流中启用：

1. **实现算法**：在 `hydrosis/routing/custom_decay.py`（示例路径）中编写：

```python
from hydrosis.routing.base import RoutingModel, RoutingModelConfig

class LagDecayRouting(RoutingModel):
    def __init__(self, parameters):
        super().__init__(parameters)
        self.lag_steps = int(self.parameters.get("lag_steps", 1))
        self.decay = float(self.parameters.get("decay", 0.9))

    def route(self, subbasin, inflow):
        padding = [0.0] * self.lag_steps
        core = inflow[:-self.lag_steps] if self.lag_steps < len(inflow) else []
        return padding + [value * self.decay for value in core]

RoutingModelConfig.register("lag_decay", LagDecayRouting)
```

2. **更新配置**：在 `config/example_model.yaml` 的 `routing_models` 中新增条目 `model_type: lag_decay` 并给出衰减参数，或在场景 `modifications` 中覆盖某个子流域的 `routing_model`。【F:config/example_model.yaml†L70-L131】
3. **加载并运行**：复用示例脚本 `examples/run_sample_workflow.py`，其会解析配置、解析情景并执行工作流；新增模型会被自动实例化并参与评估、报告生成，无需修改脚本逻辑。【F:examples/run_sample_workflow.py†L137-L179】
4. **编写测试**：参考 `tests/test_examples.py` 构建针对新模型的参数区配置与情景切换断言，确保 `RoutingModelConfig` 能正确实例化注册类。【F:tests/test_examples.py†L18-L92】

通过该流程，开发者可以快速将科研算法或行业调度策略注入 HydroSIS，同时保持配置驱动、测试可复现与报告输出一致。
